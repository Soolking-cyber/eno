## How trip DDL gets applied (⚠️ read before any schema task)

**Never `prisma db push` on this repo.** `public.Profile` has a cross-schema FK to `auth.users`
(`profile_auth_fk`), which makes **every** Prisma introspection fail with `P4002` — `db push` and
`migrate diff` both die on it. CLAUDE.md:100 documents a drop-FK/push/restore-FK dance, but a
whole-schema reconcile is also the wrong tool here: `visa_applications`, `next_cache`, `rl_window`
and others live in `public` and are **deliberately absent** from `schema.prisma`.

The procedure that worked for T301, and that Alex will repeat: hand-write additive DDL that mirrors
the conventions of an existing sibling table (dump it with `information_schema.columns` +
`pg_constraint` + `pg_indexes` first), apply it in a transaction over `DIRECT_URL`, then prove
Prisma and the DDL agree with a round-trip inside a rolled-back transaction. **DDL lands BEFORE the
code deploys**, or the endpoint 503s in the gap.
